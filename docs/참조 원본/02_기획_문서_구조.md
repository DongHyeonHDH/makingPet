# 02. 기획 문서 구조 (템플릿)

> `기획/` 폴더 = **단일 진실 소스(SSoT)**. 코드보다 문서가 먼저 바뀐다.
> 아래 트리를 그대로 만들고, 각 문서는 제시된 **섹션 양식**을 채운다. 개인 프로젝트면 `01_planning`의 역할 분담·의식 문서는 생략 가능.

---

### 문서 공통 규칙
- 문서 맨 위에 **변경 박스**를 둔다: `> ⚠️ YYYY-MM-DD 회의 반영 — 본 박스가 최신, 본문과 충돌 시 박스 우선`
- 상단에 **비유 한 줄**을 둔다. 원본 프로젝트가 쓰던 스타일로, 처음 보는 사람이 개념을 빨리 잡게 돕는다(선택).
- 모르는 용어는 `00_overview/01_용어집.md` 링크로 연결한다.
- API(`04_api`), ERD(`03_erd`), 일정(`01_planning`) 변경은 **승인 후** 반영한다. 파트 가이드는 자유롭게 수정한다.

## 2. 문서별 섹션 양식

### 2-1. `README.md`
```markdown
# {{PROJECT_NAME}} · 기획 문서
> 이 폴더는 단일 진실 소스(SSoT). 코드보다 먼저 바뀐다.

## 폴더 구성
| 폴더 | 무엇이 들어있나 | 누가 자주 보나 |

## 처음 들어온 사람의 30분 온보딩 코스
1. 00_overview/00_프로젝트_개요.md (5분)
2. 01_planning/01_마일스톤_일정.md (5분)
3. 02_architecture/01_시스템_아키텍처.md (5분)
4. 08_collaboration/01_Git_브랜치_PR_규칙.md (5분)
5. 07_part_guides/내_파트.md (10분)

## 핵심 원칙 (TL;DR)
1. 컨트랙트 먼저, 구현 나중
2. 남의 도메인 엔티티 직접 import 금지
3. DB 스키마 변경 책임자 1명
4. 모든 응답 ApiResponse<T>
5. 핵심 시나리오 테스트 머지 전 필수

## 문서를 바꿀 때
## 도메인 ↔ 담당자 커버리지 매트릭스
| 도메인 패키지 | 담당 | 비고 |
```

장 단위로 분류한다. A 도메인 용어, B Spring, C JPA/DB, D 보안/JWT, E HTTP/API, F 인프라/Docker, G 테스트, H Git/협업. 각 항목은 `| 용어 | 한 줄 정의 | 예시 / 관련 문서 |` 형식으로 쓴다.

# 파트 가이드 — {Domain}

## 2. 패키지 / 파일 소유권

### 절대 손대지 말 것
## 3. 외부 컨트랙트 (내가 제공하는 service 메서드 / API)

### 2-10. `08_collaboration/`

**01_Git_브랜치_PR_규칙.md**
```
feature/<domain>-<주제>/#<이슈>  ─PR→  dev  ─PR→  prod  ─PR→  main
prefix: feature / fix / chore / docs / refactor
```
| 브랜치 | 의미 | 머지 출처 | 보호 |
|---|---|---|---|
| feature/* | 1~3일 작업 | (dev에서 분기) | - |
| dev | 통합, CI 테스트 그린 유지 | feature/* | PR 필수 |
| prod | 운영 프로파일 검증 | dev | PR 필수 |
| main | 배포본, 태깅 및 배포 트리거 | prod | PR + 승인 |

- 보호 브랜치에 직접 push하지 않는다. 한 PR에는 목적 하나만 담고, 변경량은 400 LoC 미만을 권장한다.
- 브랜치 최신화는 merge로 한다(rebase 금지 정책은 팀 선택 사항).
- PR 본문에 `Closes #N`을 적어 이슈와 연결한다.

**PR 템플릿 (`.github/PULL_REQUEST_TEMPLATE.md`)**
```markdown
## 🔗 관련 이슈
- close #
## 왜
## 어떻게
## 영향 받는 도메인
- [ ] {domain} ...
## 테스트
## 체크리스트
- [ ] `./gradlew clean compileJava test` 통과
- [ ] 응답이 `ApiResponse<T>` 래핑
- [ ] API 변경 시 `기획/04_api/` 동기 수정
## ERD/API 변경
- [ ] 없음 / [ ] 있음 → 같은 PR에서 기획 문서 수정
## 기타
```

**이슈 템플릿 (`.github/ISSUE_TEMPLATE/{type}_issues_template.md`)** — type은 feature, bugfix, refactor, chore, test, add, mod 중 하나
```markdown
---
name: Feature
about: 새로운 사용자 기능 또는 화면/API 흐름 제안
title: "[Feature] "
labels: feature
assignees: ''
---
## 🧩 기능 개요
## ✅ 작업 목록
- [ ]
## 🔍 완료 조건
- [ ]
## 💬 참고 사항
```

**02_코딩_컨벤션.md**: 언어 정책, 패키지 규칙, 네이밍(01_프로젝트_트리.md 5절), 응답/예외 규칙, 트랜잭션(`@Transactional(readOnly = true)` 기본, 변경 메서드만 쓰기 트랜잭션), 테스트 BDD 네이밍을 정리한다.

**03_충돌_방지_플레이북.md**: 공용 파일(`SecurityConfig`, `ErrorCode`, `application.yml`, `build.gradle`) 수정 규칙을 정한다. 한 PR에서 공용 파일 수정은 최소화하고, 게이트키퍼를 지정하고, enum에는 도메인별 섹션 주석을 달아 append-only로 관리한다.

**04_코드_리뷰_체크리스트.md**: 권한 체크, N+1, 트랜잭션 경계, 예외 코드 사전 준수, 입력 검증, 테스트 존재 여부를 점검한다.
