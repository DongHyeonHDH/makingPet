# 04. 게임 동시성 설계 — 보상 원자 처리 · 게임 세션 잠금 · 멱등 키

> ⚠️ 2026-11-17 결정 반영 — 본 박스가 최신, 본문과 충돌 시 박스 우선
> - 동시 플레이 방어는 3겹: **① 단일 기기 로그인**(`03_인증_토큰_설계.md`) **② 게임 세션 잠금**(Redis) **③ 보상 원자 처리**(DB)
> - 게임 결과·보상량은 **서버가 결정**한다. 클라이언트는 입력(낼 손 등)만 보낸다
> - 재화가 움직이는 모든 `POST`는 **`Idempotency-Key` 헤더 필수**
> - 하루 기준은 **KST 00:00**
> - 테이블(4장)은 **초안**이다. `03_erd/01_ERD.md` 승인 후 확정

> 비유: 놀이공원 기구 하나에 **입장 팔찌(세션 잠금)**를 한 개만 채워 주고, 경품은 **도장 카드(DB 유니크)**로 하루 한 번만 찍어 준다. 팔찌를 어떻게든 두 개 얻어도 도장은 한 번만 찍힌다.

## 0. 결정 요약

| 위협 | 방어 | 위치 | 뚫리면 |
|---|---|---|---|
| 다른 기기에서 동시 접속 | 단일 기기 로그인 | 인증 (03 문서) | ②③이 막음 |
| 같은 브라우저 탭 여러 개로 동시 진행 | 게임 세션 잠금 | Redis | ③이 막음 |
| 더블클릭, 네트워크 재시도 | 멱등 키 | DB 유니크 | ③이 막음 |
| 1일 1회 보상 중복, 재화 마이너스 | 조건부 UPDATE / 유니크 제약 | DB (트랜잭션) | **마지막 방어선, 뚫리면 안 됨** |
| 결과 조작 (이겼다고 보내기) | 서버 권위 판정 | 서비스 로직 | - |

**원칙 세 가지**
1. **DB가 진실이다.** Redis는 잠금과 빠른 거절에만 쓴다. Redis가 날아가도 중복 지급은 0이어야 한다.
2. **클라이언트 차단은 UX일 뿐이다.** 탭 감지(BroadcastChannel)는 안내 문구용이고 보안 장치로 세지 않는다.
3. **결과를 클라이언트에게 묻지 않는다.** 승패, 확률, 보상량은 서버가 정하고 기록한다.

## 1. 전체 흐름 (가위바위보 1회 플레이)

```
Client                              Server
  │ POST /api/games/sessions {gameType:RPS}
  │──────────────────────────────────▶ ② 세션 잠금 획득 (SET NX)
  │◀────────── 201 {sessionId, expiresIn}
  │
  │ POST /api/games/rps/plays
  │   Idempotency-Key: 7c1e...
  │   {sessionId, hand: ROCK}
  │──────────────────────────────────▶ ② 세션 확인 + TTL 연장 (Lua)
  │                                     멱등 키로 기존 결과 조회 → 있으면 그대로 반환
  │                                   ┌ @Transactional ─────────────────────────┐
  │                                   │ ③ daily_quota 1회 소비 (조건부 UPDATE)   │
  │                                   │   서버 난수로 상대 손 결정, 승패 판정      │
  │                                   │ ③ wallet 적립 (원자적 UPDATE)            │
  │                                   │   currency_ledger 기록                    │
  │                                   │   game_play 기록 (멱등 키 UNIQUE)          │
  │                                   └──────────────────────────────────────────┘
  │◀────────── 201 {result, serverHand, reward, balance}
  │
  │ DELETE /api/games/sessions/{sessionId}
  │──────────────────────────────────▶ ② 세션 해제 (내 세션일 때만 DEL)
```

**같은 브라우저 탭 B가 동시에 시작하면**
```
탭 B: POST /api/games/sessions  ─▶ 409 GAME_SESSION_ALREADY_ACTIVE
      UI: "다른 창에서 게임이 진행 중입니다. [여기서 이어하기]"
      "여기서 이어하기" ─▶ POST /api/games/sessions {takeover:true} ─▶ 탭 B가 세션 소유
탭 A: 다음 플레이 요청 ─▶ 409 GAME_SESSION_MISMATCH  ("다른 창에서 이어서 진행 중")
```
> takeover를 허용해도 **동시에 진행 가능한 세션은 항상 하나**다. 탭이 비정상 종료되어 잠금이 남았을 때 TTL(2분)을 기다리지 않게 해준다.

## 2. 보상 원자 처리 (③, 필수)

### 2-1. 패턴 선택

| 상황 | 패턴 | SQL 핵심 |
|---|---|---|
| 1일 N회 제한 (출석 N=1, 가위바위보 N=1, 빠칭코 N=?) | 쿼터 행 + **조건부 UPDATE** | `UPDATE daily_quota SET used_count = used_count + 1 WHERE ... AND used_count < :limit` → 영향 행 0이면 초과 |
| 재화 적립 | **원자적 UPDATE** | `UPDATE wallet SET balance = balance + :amount WHERE user_id = :uid` |
| 재화 차감 (펫 뽑기 등) | **조건부 UPDATE** | `... SET balance = balance - :cost WHERE user_id = :uid AND balance >= :cost` → 0이면 잔액 부족 |
| 같은 요청 재전송 | **멱등 키 UNIQUE** | `UNIQUE (user_id, idempotency_key)` on `game_play` |

**하지 말아야 할 것** (흔한 함정)
- `SELECT` 로 확인 후 `UPDATE` (check-then-act): 두 요청이 동시에 "아직 0회"를 읽고 둘 다 지급한다.
- JPA로 엔티티를 읽어 `wallet.add(100)` 후 dirty checking: 같은 문제(lost update). 써야 한다면 `@Version` 낙관적 락 + 재시도가 필요한데, 위 조건부 UPDATE가 더 단순하다.
- Redis 카운터만으로 1일 1회 제한: Redis 장애·재시작 시 카운터가 사라지면 하루에 두 번 받을 수 있다.

### 2-2. 하루 기준 (KST)
```java
@Component
public class GameClock {
    public static final ZoneId ZONE = ZoneId.of("Asia/Seoul");
    private final Clock clock;
    public GameClock(Clock clock) { this.clock = clock; }       // 테스트에서 고정 Clock 주입
    public LocalDate today() { return LocalDate.now(clock.withZone(ZONE)); }
}
```
- 클라이언트가 보낸 날짜는 쓰지 않는다. 서버 타임존(UTC)과 무관하게 `GameClock.today()`만 쓴다.
- 23:59:59에 시작해 00:00:01에 끝난 플레이는 **플레이 요청을 처리한 시각**의 날짜로 센다.

### 2-3. `DailyQuotaRepository` (JdbcTemplate)
```java
@Repository
@RequiredArgsConstructor
public class DailyQuotaRepository {
    private final JdbcTemplate jdbc;

    /** 남은 횟수가 있으면 1 소비하고 true. 동시 요청은 행 잠금으로 직렬화된다 */
    public boolean tryConsume(Long userId, QuotaType type, LocalDate date, int limit) {
        jdbc.update("""
                INSERT IGNORE INTO daily_quota (user_id, quota_type, quota_date, used_count, created_at, updated_at)
                VALUES (?, ?, ?, 0, NOW(6), NOW(6))
                """, userId, type.name(), date);
        int updated = jdbc.update("""
                UPDATE daily_quota SET used_count = used_count + 1, updated_at = NOW(6)
                WHERE user_id = ? AND quota_type = ? AND quota_date = ? AND used_count < ?
                """, userId, type.name(), date, limit);
        return updated == 1;
    }
}
```
> JPA 대신 JdbcTemplate을 쓰는 이유: 조건부 UPDATE의 **영향 행 수**가 판정 결과이기 때문이다. `INSERT IGNORE`는 중복 키여도 트랜잭션을 깨지 않는다.

### 2-4. `WalletService` (wallet 도메인)
```java
@Service
@RequiredArgsConstructor
public class WalletService {
    private final JdbcTemplate jdbc;
    private final CurrencyLedgerRepository ledgerRepository;

    /** 호출자의 트랜잭션 안에서만 호출한다 (MANDATORY) */
    @Transactional(propagation = Propagation.MANDATORY)
    public long credit(Long userId, long amount, LedgerReason reason, String refType, Long refId) {
        PreConditions.validate(amount > 0, ErrorCode.VALIDATION_FAILED);
        int updated = jdbc.update("UPDATE wallet SET balance = balance + ?, updated_at = NOW(6) WHERE user_id = ?",
                amount, userId);
        PreConditions.validate(updated == 1, ErrorCode.WALLET_NOT_FOUND);
        return recordLedger(userId, amount, reason, refType, refId);
    }

    @Transactional(propagation = Propagation.MANDATORY)
    public long debit(Long userId, long amount, LedgerReason reason, String refType, Long refId) {
        PreConditions.validate(amount > 0, ErrorCode.VALIDATION_FAILED);
        int updated = jdbc.update("""
                UPDATE wallet SET balance = balance - ?, updated_at = NOW(6)
                WHERE user_id = ? AND balance >= ?
                """, amount, userId, amount);
        PreConditions.validate(updated == 1, ErrorCode.CURRENCY_INSUFFICIENT);
        return recordLedger(userId, -amount, reason, refType, refId);
    }

    private long recordLedger(Long userId, long delta, LedgerReason reason, String refType, Long refId) {
        Long balanceAfter = jdbc.queryForObject("SELECT balance FROM wallet WHERE user_id = ?", Long.class, userId);
        ledgerRepository.save(CurrencyLedger.of(userId, delta, balanceAfter, reason, refType, refId));
        return balanceAfter;
    }
}
```
> 같은 트랜잭션 안에서 UPDATE가 행 잠금을 쥐고 있으므로 직후 SELECT의 잔액은 정확하다. 원장(ledger)은 **잔액을 다시 계산할 수 있는 근거**이자 CS 대응 자료다.

### 2-5. 플레이 처리 (`game` 도메인)
```java
/** 트랜잭션 밖: 세션 확인, 멱등 재조회, 예외 번역 */
@Service
@RequiredArgsConstructor
public class RpsPlayFacade {
    private final GameSessionService sessionService;
    private final RpsPlayService playService;
    private final GamePlayRepository playRepository;

    public RpsPlayResponse play(CurrentUser user, String idempotencyKey, RpsPlayRequest request) {
        PreConditions.validate(isValidKey(idempotencyKey), ErrorCode.IDEMPOTENCY_KEY_REQUIRED);
        sessionService.validateAndTouch(user.getId(), request.sessionId(), GameType.RPS);

        Optional<GamePlay> replay = playRepository.findByUserIdAndIdempotencyKey(user.getId(), idempotencyKey);
        if (replay.isPresent()) return RpsPlayResponse.from(replay.get());          // 재전송 → 같은 결과

        try {
            return playService.play(user.getId(), idempotencyKey, request.hand());
        } catch (DataIntegrityViolationException | BusinessException e) {
            // 동시에 같은 키로 들어온 두 번째 요청: 먼저 커밋된 결과를 돌려준다
            return playRepository.findByUserIdAndIdempotencyKey(user.getId(), idempotencyKey)
                    .map(RpsPlayResponse::from)
                    .orElseThrow(() -> e instanceof BusinessException be ? be
                            : new BusinessException(ErrorCode.INTERNAL_ERROR));
        }
    }

    private static boolean isValidKey(String key) {
        if (key == null) return false;
        try { UUID.fromString(key); return true; } catch (IllegalArgumentException e) { return false; }
    }
}

/** 트랜잭션 안: 쿼터 → 판정 → 지급 → 기록. 하나라도 실패하면 전부 롤백 */
@Service
@RequiredArgsConstructor
public class RpsPlayService {
    private static final SecureRandom RANDOM = new SecureRandom();
    private final DailyQuotaRepository quotaRepository;
    private final WalletService walletService;
    private final GamePlayRepository playRepository;
    private final GameClock clock;
    private final GameRewardPolicy rewardPolicy;      // 보상량은 서버 설정

    @Transactional
    public RpsPlayResponse play(Long userId, String idempotencyKey, Hand hand) {
        boolean consumed = quotaRepository.tryConsume(userId, QuotaType.RPS, clock.today(), rewardPolicy.rpsDailyLimit());
        PreConditions.validate(consumed, ErrorCode.DAILY_LIMIT_EXCEEDED);

        Hand serverHand = Hand.values()[RANDOM.nextInt(Hand.values().length)];
        RpsResult result = RpsResult.judge(hand, serverHand);
        long reward = rewardPolicy.rpsReward(result);

        GamePlay savedPlay = playRepository.saveAndFlush(          // UNIQUE(user_id, idempotency_key)
                GamePlay.rps(userId, idempotencyKey, clock.today(), hand, serverHand, result, reward));
        long balance = reward > 0
                ? walletService.credit(userId, reward, LedgerReason.GAME_REWARD, "GAME_PLAY", savedPlay.getId())
                : walletService.currentBalance(userId);
        return RpsPlayResponse.of(savedPlay, balance);
    }
}
```
> 동시 요청 2개가 같은 멱등 키로 오면: 첫 요청이 쿼터 행을 잠그고 커밋 → 두 번째는 잠금을 기다렸다가 `DAILY_LIMIT_EXCEEDED`(또는 유니크 위반) → Facade가 멱등 키로 다시 조회해 **첫 요청의 결과**를 돌려준다. 사용자는 같은 응답 두 번, 지급은 한 번.
>
> `walletService.currentBalance`는 단순 조회 메서드다(`@Transactional(readOnly = true)`).

## 3. 게임 세션 잠금 (②)

### 3-1. Redis 키

| 키 | 타입 | 값 | TTL | 용도 |
|---|---|---|---|---|
| `game:session:<userId>` | String | `<sessionId>:<gameType>` | 120초, 요청마다 연장 | 계정당 진행 중 게임 1개 |

- 세션 하나 = 게임 한 판(또는 한 번의 게임 화면 체류). 탭이 아니라 **세션 ID**로 소유를 판단한다.
- 마지막 요청 후 2분간 아무 요청이 없으면 자동 해제. 화면에 머무는 동안 프론트가 60초마다 heartbeat.

### 3-2. Lua 스크립트 (비교 후 처리, 원자적)
```lua
-- acquire.lua  KEYS[1]=game:session:<userId>  ARGV[1]=value ARGV[2]=ttl ARGV[3]=takeover(0/1)
if ARGV[3] == '1' then
  redis.call('SET', KEYS[1], ARGV[1], 'EX', ARGV[2])
  return 1
end
if redis.call('SET', KEYS[1], ARGV[1], 'NX', 'EX', ARGV[2]) then return 1 end
return 0
```
```lua
-- touch.lua  KEYS[1]  ARGV[1]=value ARGV[2]=ttl
local cur = redis.call('GET', KEYS[1])
if not cur then return -1 end                 -- 만료/없음
if cur ~= ARGV[1] then return 0 end           -- 다른 세션이 소유
redis.call('EXPIRE', KEYS[1], ARGV[2])
return 1
```
```lua
-- release.lua  KEYS[1]  ARGV[1]=value
if redis.call('GET', KEYS[1]) == ARGV[1] then return redis.call('DEL', KEYS[1]) end
return 0
```
> 그냥 `DEL`하면 takeover한 다른 탭의 세션을 지울 수 있다. 반드시 "내 값일 때만" 지운다.

### 3-3. `GameSessionService`
```java
@Service
@RequiredArgsConstructor
public class GameSessionService {
    private static final Duration TTL = Duration.ofSeconds(120);
    private static final RedisScript<Long> ACQUIRE = RedisScript.of(new ClassPathResource("redis/game_session_acquire.lua"), Long.class);
    private static final RedisScript<Long> TOUCH   = RedisScript.of(new ClassPathResource("redis/game_session_touch.lua"), Long.class);
    private static final RedisScript<Long> RELEASE = RedisScript.of(new ClassPathResource("redis/game_session_release.lua"), Long.class);

    private final StringRedisTemplate redis;

    public GameSessionResponse start(Long userId, GameType type, boolean takeover) {
        String sessionId = UUID.randomUUID().toString();
        Long ok = execute(ACQUIRE, userId, value(sessionId, type), String.valueOf(TTL.toSeconds()), takeover ? "1" : "0");
        PreConditions.validate(ok == 1L, ErrorCode.GAME_SESSION_ALREADY_ACTIVE);
        return new GameSessionResponse(sessionId, type, TTL.toSeconds());
    }

    public void validateAndTouch(Long userId, String sessionId, GameType type) {
        Long r = execute(TOUCH, userId, value(sessionId, type), String.valueOf(TTL.toSeconds()));
        PreConditions.validate(r != -1L, ErrorCode.GAME_SESSION_NOT_FOUND);
        PreConditions.validate(r == 1L, ErrorCode.GAME_SESSION_MISMATCH);
    }

    public void end(Long userId, String sessionId, GameType type) {
        execute(RELEASE, userId, value(sessionId, type));            // 멱등: 이미 없으면 무시
    }

    private Long execute(RedisScript<Long> script, Long userId, String... args) {
        try {
            return redis.execute(script, List.of("game:session:" + userId), (Object[]) args);
        } catch (DataAccessException e) {
            throw new BusinessException(ErrorCode.GAME_SESSION_UNAVAILABLE);   // fail-closed
        }
    }

    private static String value(String sessionId, GameType type) { return sessionId + ":" + type.name(); }
}
```

### 3-4. Redis 장애 시
게임 세션 잠금은 **fail-closed**(503 `GAME_SESSION_UNAVAILABLE`)로 둔다. 게임이 잠시 멈출 뿐 재화는 안전하다. 설령 잠금이 없어도 ③이 중복 지급을 막으므로, 이건 보안보다 **게임 진행의 일관성**을 위한 선택이다.

### 3-5. 프론트 (UX 보조)
```ts
// 같은 브라우저 탭끼리 "진행 중" 상태 공유 — 안내 문구용, 보안 장치 아님
const ch = new BroadcastChannel('game-session');
ch.onmessage = (e) => { if (e.data.type === 'STARTED') showBanner('다른 창에서 게임이 진행 중입니다'); };
// 세션 시작 성공 시 ch.postMessage({ type: 'STARTED' })
// 화면 체류 중 60초마다 PUT /api/games/sessions/{id}/heartbeat
// 화면 이탈(pagehide) 시 navigator.sendBeacon 대신 fetch(..., { method:'DELETE', keepalive:true })
```
> `sendBeacon`은 POST만 되고 Authorization 헤더를 못 붙이므로 `fetch keepalive`를 쓴다. 실패해도 TTL이 정리한다.

## 6. 패키지 소유권

```
game/
├─ controller/  GameSessionController, RpsController
├─ service/     GameSessionService, RpsPlayFacade, RpsPlayService, GameClock, GameRewardPolicy
├─ repository/  GamePlayRepository, DailyQuotaRepository (JdbcTemplate)
├─ domain/      GamePlay, GameType, Hand, RpsResult, QuotaType
└─ dto/         GameSessionStartRequest, GameSessionResponse, RpsPlayRequest, RpsPlayResponse
wallet/
├─ controller/  WalletController (GET /api/wallets/me)
├─ service/     WalletService            ← 다른 도메인은 이것만 호출
├─ repository/  CurrencyLedgerRepository
├─ domain/      Wallet, CurrencyLedger, LedgerReason
└─ dto/
resources/redis/ game_session_acquire.lua, game_session_touch.lua, game_session_release.lua
```
- `game`은 `wallet`의 **service만** 호출한다(엔티티·리포지토리 import 금지, `01_프로젝트_트리.md` 4절).
- 출석(attendance)과 펫 뽑기(gacha)도 같은 패턴을 쓴다: 출석은 `DailyQuota(ATTENDANCE, limit=1)` + `credit`, 뽑기는 `debit` + 멱등 키.
- `WalletService` 메서드가 `Propagation.MANDATORY`라 호출자가 트랜잭션을 반드시 연다. 트랜잭션 밖 호출은 즉시 예외가 나서 실수가 드러난다.

## 7. 테스트 시나리오

동시성 테스트는 **실제 MySQL과 Redis**로 돌린다. `INSERT IGNORE`·행 잠금·Lua는 H2나 Mock으로 검증할 수 없다. Testcontainers(MySQL 8, Redis 7) 도입을 권장한다.

```
Describe_RpsPlayService_play는
  Context_오늘_처음_플레이한_경우          └ It_결과를_기록하고_보상을_지급한다()
  Context_오늘_이미_플레이한_경우          └ It_DAILY_LIMIT_EXCEEDED를_던진다()
  Context_같은_사용자가_10개_스레드로_동시에_플레이한_경우 └ It_성공은_정확히_1건이고_잔액은_보상_1회분만_늘어난다()
  Context_KST_자정이_지난_경우             └ It_새_날짜로_다시_플레이할_수_있다()   (고정 Clock)

Describe_RpsPlayFacade_play는
  Context_같은_Idempotency-Key로_재전송한_경우      └ It_같은_결과를_반환하고_추가_지급하지_않는다()
  Context_같은_키로_동시에_두_번_요청한_경우         └ It_둘_다_같은_결과를_받고_지급은_1회다()
  Context_Idempotency-Key가_없는_경우             └ It_IDEMPOTENCY_KEY_REQUIRED를_던진다()

Describe_WalletService_debit은
  Context_잔액이_부족한_경우                └ It_CURRENCY_INSUFFICIENT를_던지고_잔액은_그대로다()
  Context_동시에_잔액보다_많이_차감하려는_경우 └ It_잔액이_음수가_되지_않는다()
  Context_트랜잭션_밖에서_호출한_경우        └ It_IllegalTransactionStateException을_던진다()

Describe_GameSessionService는
  Context_진행_중인_세션이_있는데_start한_경우    └ It_GAME_SESSION_ALREADY_ACTIVE를_던진다()
  Context_takeover로_start한_경우               └ It_이전_세션의_touch는_MISMATCH가_된다()
  Context_이전_세션이_end를_호출한_경우          └ It_새_세션은_지워지지_않는다()
  Context_TTL이_지난_경우                       └ It_GAME_SESSION_NOT_FOUND를_던진다()
```
